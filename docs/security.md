# Security

- **Regions are isolated by the database.** Row-level security (forced, with a database role that cannot bypass it) limits every query to the caller's role, region or point of sale. Grossistes have no accounts: their stock belongs to a region. A forgotten filter in the code cannot leak another region's data; tests forge filters to prove it.
- **Sign-in.** Argon2id passwords (admission-controlled so a flood cannot exhaust the server), random 256-bit session tokens stored hashed, sessions that last 90 days without use (7 days for the admin) and are renewed each time the app is used, attempt limits per address and per email, identical answers for unknown and wrong accounts. The admin also needs a TOTP code from an authenticator app; each code works once. The secret is stored encrypted with `MFA_ENCRYPTION_KEY`.
- **Invitations and recovery** use one-time 8-character codes, valid only together with the person's email, stored hashed, expiring (72 hours / 30 minutes) and removed from the job queue once handled.
- **Approvals are enforced by the server**, not by the screens: a pending point of sale cannot sell, a pending member cannot sign in, unapproved stock is not stock.
- **Uploads** are streamed to disk with a size limit per purpose, checked by their real first bytes (JPEG, PNG, WebP, PDF, MP4), stored under server-generated names, and served with `nosniff`. Proof photos are readable only by their author, the admin and the region's responsable.
- **Append-only history** (stock movements, sale revisions, wallet entries, audit log) is enforced by database triggers.
- **Money** is whole millimes in 64-bit integers; payouts lock the person's wallet so concurrent requests cannot overspend.
- **Transport and edge:** HTTPS only (Cloudflare Full-strict, origin restricted to Cloudflare), HSTS, request rate limits, small JSON bodies, `no-store` on API responses, containers read-only with dropped capabilities.
- **CSV exports** neutralise cells that start with `=`, `+`, `-` or `@`.
- **Secrets** (`backend.env`, signing keys, the admin setup file) never enter the repository.
- **Account deletion** erases personal data at once, in one transaction (identity, password, MFA secret, sessions, codes, notifications), keeps the business records without a name, and can never be undone or reactivated. It asks for the password and is rate-limited.
- **On the phone:** the session token is in the system keychain (iOS) / encrypted storage (Android); business data and the offline outbox are excluded from cloud backups; screenshots and the recents preview are blocked in Android release builds and covered on iOS when the app goes to the background. No analytics or tracking SDK is included.
- **Photos and documents kept on the phone** (to open at once and spare mobile data) live in the app's private folder, excluded from backups, capped at 200 MB, and are deleted at sign-out and account deletion.
- **Push alerts** (Apple and Firebase) are tied to a signed-in session: signing out, a new password or a deleted account ends the session and the phone stops receiving alerts. Alerts carry only the notification's sentence, never documents or amounts beyond what the inbox shows.
- **The Firebase service-account key** lives only in the root-only `/etc/biobalance/backend.env` on the server (never in the repository or the app); the app carries only the project's public identifiers.

- **WhatsApp codes (2026-10).** A code sent by WhatsApp is as sensitive as one sent by email: it is single-use, short-lived, never kept after the job finishes, never sent twice after use or expiry, and the password-reset answer stays identical whether or not an account exists. The WAHA container is reachable only on the private network (its dashboard only on the server's loopback); its API key is a server secret. The unofficial session can be lost or blocked: the email path is independent.

- **Planning and position (2026-11).** The position is read only when a responsable taps "I'm here" or "I'm leaving" with the app open (foreground permission only; no background location, and the location plugin's foreground service is removed from the Android manifest). It is kept with the check-in for **12 months** in an **append-only** table (the database refuses an update, and a delete before the 12 months), visible only to the responsable and the admin (row-level security; the test region stays hidden from the admin). A position is evidence, not proof: it shows where a phone was, and a location-faking app can fake it (the Android flag is recorded; the iPhone offers none). The calendar link (`/cal/<token>.ics`) is a 256-bit secret in the address: nobody can guess it, a new one cancels the old, a deactivated or deleted responsable's link answers 404, throttling applies, and the answer is `private, no-store, no-transform`. The feed carries the place's name, address, time and note, nothing else.

- **Transfers between paras (2026-11).** Row-level security: a team member sees the transfers where their para is on either side, a responsable those of their region, the admin all (the test region hidden); another region sees nothing, not even that one exists (404). The other para's stock and name are read by trusted server code only to check and show a transfer; a team member never reads the other para's stock. Only paras of the same *active* group can exchange; the admin alone decides; the quantity changes are append-only (`TransferRevision`); the stock moves in one transaction and can never go below zero.

- **Returns (2026-11).** Row-level security: a responsable sees the returns of their own region, the admin all (the test region hidden), a team member none. Only the admin can move or add quantities (a responsable's request is a take-out for a para of their own region, 404 for another's); a move may cross regions, and it is the admin's alone. The quantity changes are append-only (`ReturnRevision`); the stock moves in one transaction and never goes below zero.
