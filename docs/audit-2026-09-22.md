# Audit de robustesse — 22 septembre 2026

L’audit porte sur le code applicatif Flutter/NestJS, les transactions PostgreSQL, la synchronisation SQLite, les contrôles d’accès, les médias, les notifications, les workers et les outils de déploiement. Le point de départ est `6e8ec3b` sur `codex/biobalance-app`. Les dépendances tierces et les binaires ne sont pas assimilés à du code relu manuellement. Un audit de code ne prouve pas l’absence de tout défaut.

## Sécurité corrigée

| Constat sur le point de départ | Correction |
|---|---|
| Une connexion déjà engagée pouvait créer une session avec l’ancien mot de passe après une réinitialisation | Vérification du hash courant sous verrou, émission de session et MFA dans la même transaction ; révocation et invalidation des anciens codes de récupération |
| Les codes d’activation/récupération invalides déclenchaient Argon2 avant validation | Validation préalable, limites par origine/code, admission de quatre calculs Argon2 par processus et réponse 429 explicite |
| Plusieurs chemins globaux utilisaient des droits capturés par le guard | `Database.authenticated` relit identité, session et rôle dans la transaction ; contrôles partagés pour magasins, catalogue, rapports, notifications et contenus |
| Des téléversements autorisés pouvaient remplir indéfiniment le stockage partagé | Réservation atomique des octets, limites par magasin/propriétaire, marge disque, expiration des transferts abandonnés et nettoyage des sources après traitement |
| Nombre d’appareils et diffusion push non bornés | Dix appareils actifs par compte, rotation par session/plateforme, suppression à la déconnexion, nettoyage des endpoints périmés et diffusion limitée même pour les anciennes inscriptions |
| Un refus de session confirmé pouvait être oublié au redémarrage mobile | Refus conservé dans la session sécurisée avec son compte/token ; aucune remise à zéro par une réponse tardive ; brouillons et outbox conservés |
| Un autre logiciel installé pouvait recevoir un lien de récupération `biobalance://` | Retrait des handlers du schéma privé ; codes manuels par défaut et liens HTTPS limités à l’hôte vérifié configuré |
| Le corps d’un téléversement était lu avant authentification | Identité et propriété vérifiées avant lecture ; huit admissions simultanées par API ; limites supplémentaires Nginx |
| Compteurs d’authentification expirés conservés sans limite | Nettoyage horaire par lots après 24 heures, index de rétention ; les historiques métier restent conservés |

Le rapport Codex Security décrit les défauts du commit de départ, pas des défauts laissés ouverts dans les corrections. Il consolide neuf constats : un élevé, sept moyens et un faible. Les hypothèses nécessitant déjà la compromission de l’OS ou d’un éditeur de dépendances ne sont pas présentées comme des exploitations démontrées de l’application.

## Cohérence et qualité du code

- Éditions concurrentes du catalogue : une seule modification d’une version donnée est acceptée ; l’autre reçoit un conflit.
- Limiteur d’authentification : remise à zéro et incrément atomiques, y compris lors d’une fenêtre concurrente.
- Curseurs : JSON/UUID/date invalides et entiers au-delà de PostgreSQL sont rejetés comme erreurs client.
- Toutes les demandes de récompense et commandes non terminées, les livraisons en cours et les récompenses sont disponibles par pages de snapshot cohérentes. Un magasin dépassant 100 demandes ne perd plus ses éléments anciens. Les historiques terminés gardent une fenêtre récente.
- Les cadeaux en produit ne déclarent plus arbitrairement un manque de stock après les mille premiers lots. La recherche est bornée par les unités nécessaires et s’arrête dès que la quantité est affectée.
- Une autorisation de magasin connue comme révoquée est relue avant de rejouer l’outbox ; les opérations restent liées au compte initial.
- Un téléversement dont la réponse initiale a été perdue retrouve son identité par propriétaire, usage, magasin, taille et SHA-256. Les empreintes des fragments permettent de reprendre après suppression de la source ; un fragment altéré reste refusé.
- Les exports CSV conservent les signes et les guillemets, et neutralisent les préfixes interprétables comme formules.
- Le client Dart généré refuse les entiers fractionnaires et les discriminateurs incohérents. Les enveloppes v1 déjà enregistrées sont transmises sans réécriture.
- Transactions/reprises, erreurs HTTP, contrôle d’accès global et matérialisation des pages sont centralisés. Les requêtes d’une même transaction PostgreSQL sont séquentielles ; les workers indépendants restent concurrents.
- Le compilateur TypeScript refuse les imports/variables inutilisés. Le code backend est formaté de façon uniforme. La création d’organisation reste correcte après reprise d’une transaction d’invitation.
- La recette Android a révélé un crash lors du passage d’une vidéo diffusée à sa copie téléchargée : le contrôleur était retiré avant son indicateur « prêt ». Les deux états sont maintenant modifiés ensemble avant la destruction native asynchrone ; les callbacks utilisent le contrôleur du rendu courant. Un test force une destruction retardée pendant un rebuild.

## Données et exploitation

Migrations additives `202609220001_audit_integrity` et `202609220002_upload_identity` : réservation média, état de nettoyage, reçus de fragments, index de rétention et d’identité de téléversement. Elles ne réécrivent aucune vente, mouvement, écriture de points, révision ou opération acceptée.

Les médias finalisés restent immuables. Un transfert inachevé âgé de sept jours peut expirer ; le mobile recommence alors avec un nouvel identifiant. Les médias prêts restent disponibles, même quand leur source temporaire est supprimée. Les limites se règlent par les variables documentées dans `.env.example`.

Les sauvegardes locales ont un contrôle d’admission avant écriture : budget par défaut de 64 Gio et réserve de disque de 10 Gio. Aucun ancien backup n’est supprimé automatiquement. Lorsque le budget est atteint, la sauvegarde échoue explicitement et l’opérateur doit archiver ou supprimer des sauvegardes déjà vérifiées. Ce mécanisme ne remplace ni un quota du système de fichiers ni une sauvegarde hors serveur.

Android exclut les données de sauvegarde/transfert système ; iOS marque les répertoires opérationnels comme exclus de sauvegarde. Il n’y a pas de nouvelle couche de chiffrement SQLite et aucune donnée locale en attente n’est effacée. Les vérifications natives iOS restent à effectuer sur macOS/appareil.

La reprise Android garde le compte, les octets du payload et l’identifiant de l’opération, avec une seule vente acceptée : stock 7/version 3/points 30. La vidéo H.264 téléchargée est lue depuis le fichier vérifié après coupure réseau. L’échec initial du lecteur est conservé dans `native-first.log`, et la passe corrigée dans `native-recovery-final.log`. Ces parcours ne constituent pas une mesure de fluidité sur appareil physique.

Le laboratoire de déploiement a conservé les données existantes. Le rollback vers `6e8ec3b` puis le retour au code corrigé ont maintenu respectivement 275 et 289 lectures autorisées pendant le remplacement des API/workers. La vente rejouée conserve stock 4/version 3/points 60 ; la restauration vérifie aussi les fichiers PNG/H.264 et leurs sommes SHA-256. Ce rollback est une vérification de compatibilité dans le laboratoire, pas une recommandation de redéployer une version contenant les défauts corrigés.

Le harnais de certificats a initialement réutilisé un code TOTP déjà accepté ; le refus MFA était correct. Les probes attendent désormais le compteur suivant, et la recette complète a été rejouée avec succès. Les sessions des comptes synthétiques du laboratoire sont renouvelées après contrôle explicite de leur identité et du nom de base isolée.

La charge finale réutilise 500 magasins, 5 000 comptes, 300 000 lots et 2 022 794 ventes historiques/après exercice. Deux processus API sur la machine locale ont tenu 100 requêtes/s pendant cinq minutes puis 200 requêtes/s pendant trente secondes : 36 001 réponses, aucun échec HTTP, aucune opération rejetée, aucune itération abandonnée. Les contrôles post-charge ne trouvent aucune divergence stock/points/révisions/identités.

La première passe après durcissement a échoué au burst (lecture 591,97 ms, écriture 734,46 ms, 16 itérations abandonnées). La projection du snapshot et le contrôle global d’identité ont été regroupés pour éviter les allers-retours SQL supplémentaires ; la passe ci-dessus vérifie cette correction. L’échec reste conservé dans `load-first`, la réussite et les empreintes du code mesuré dans `load-final`. Cette mesure sans proxy ni worker concurrent ne qualifie pas la capacité du VPS de production complet.

Le build Android debug de l’entrée normale compile. Les archives APK/AAB produites avant cet audit ne contiennent pas ces corrections et doivent être reconstruites avant tout pilote. La compilation iOS, les signatures, les associations de domaine, le push réel, la capacité du VPS et les essais physiques demeurent des validations externes. Les avertissements de compatibilité future du plugin Firebase/Gradle ne sont pas des échecs de compilation, mais devront être résolus avant un changement de toolchain.

La haute disponibilité et la récupération après perte totale du VPS restent hors périmètre. L’audit et ses tests locaux ne déclarent pas la production prête.
